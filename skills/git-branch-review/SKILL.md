# Git Branch Review

## 概述

基于 git 分支差异报告，按检查清单对代码变更进行系统化审查，输出结构化 CSV 文件供人工复核。

检查清单使用语言无关的通用表述，适用于任何编程语言的项目。

## 工作流程

### 1. 获取差异报告

从用户输入中提取分支信息：
- **特性分支**：用户提供的分支名。如果用户未提供，使用 `git branch --show-current` 获取当前分支。
- **基础分支**：用户显式指定的分支。如果用户未显式指定基础分支，**固定使用 `origin/main`**。不要从环境元数据或仓库配置中自动推断。

确定两个分支后，**必须先回显给用户确认**，格式如下：

```
基础分支：origin/main
特性分支：feature-xxx
```

只有当用户回复"确认"（或明确表达同意）后，才继续后续步骤。如果用户提出修改（如更换基础分支），按用户意见调整后再次回显确认。

确认后，检查当前目录是否已有 `diff_report.md`：

**步骤 A — 存在性检查**：
- **不存在或内容为空** → 直接进入步骤 C 生成新报告
- **已存在且内容完整** → 进入步骤 B 检查是否过期

**步骤 B — 过期检查**：
从报告头部提取基础分支和特性分支的 commit hash（格式如 `origin/main (e63ef199)` 和 `feature-xxx (307dc098)`），分别与当前实际值对比：

```bash
# 获取基础分支当前 hash（取短 hash）
git rev-parse --short <基础分支>
# 获取特性分支当前 hash
git rev-parse --short HEAD
```

对比结果：
- **两个 hash 都一致** → 报告未过期，直接复用，跳过步骤 C
- **任一 hash 不一致** → 报告已过期，提示用户：

```
差异报告已过期：
  基础分支：报告记录 abc1234，当前 def5678（已变更/未变更）
  特性分支：报告记录 xyz1234，当前 uvw5678（已变更/未变更）
是否重新生成差异报告？
```

只有当用户回复"确认"后，才进入步骤 C 重新生成。

**步骤 C — 生成报告**：
使用 Skill tool 调用 `git-branch-diff` skill 生成，传入基础分支和特性分支参数。如果调用失败，提示用户手动运行 `/git-branch-diff`

### 2. 分析差异范围

阅读 diff_report.md 的文件清单部分（通常是开头的分类文件列表和变更统计），梳理：
- 变更文件总数和分布
- 按模块/目录分组
- 识别变更集中区域

**不要在此步骤阅读完整 diff 内容**，只看文件清单。具体的 diff 片段在步骤3中按需读取。

向用户简要报告差异范围，让用户确认后再开始审查。

### 3. 逐文件审查

对每个变更文件，按以下流程审查：

1. **读取该文件的 diff 片段**：从 diff_report.md 中定位到该文件的 diff 段落（用 offset/limit 或 grep 定位），只读该文件的变更内容
2. **上下文补充**：如果 diff 片段不足以判断问题，读取项目中的完整文件，理解函数签名、调用关系、数据结构
3. **按清单检查**：读取本 skill 目录下的 `references/checklist.md`，逐项对照检查
4. **自由审查**：清单之外发现的问题也应记录

审查原则：
- **宁可多读，不可漏判**：diff 片段看不懂上下文，就去读完整文件
- **逐步推进，不跳文件**：可以慢，但不能跳过
- **置信度自我评估**：每个问题必须诚实评估置信度。"可能有问题"但不确定的标为"低"
- **边审边写**：每审完几个文件就将发现的问题追加到 CSV，不要攒到最后一次性输出。这避免上下文压力导致遗漏细节
- **按需读 diff**：不要一次性读取整个 diff_report.md，而是逐文件定位到对应的 diff 段落。当变更文件很多时（50+），一次性读完整报告会撑爆上下文

### 4. 输出 CSV 文件

在工作目录生成 `code_review_<分支名>.csv`，格式如下：

```csv
问题类别,严重程度,问题置信度,问题,文件,问题阐述,处理进度,处理结果
并发安全,🟡 需关注,高,maybeReload无锁读取lastModTime,internal/smtp/auth/file_auth.go:62-68,maybeReload在无锁状态下读取lastModTime，而reload在有锁状态下写入，并发Authenticate时存在data race,待确认,
安全,🔴 严重,高,私钥提交到版本控制,config/smtp/certs/prod/server.key,自签名证书私钥提交到git，仓库泄露则TLS流量可被解密,待确认,
配置与硬编码,🟢 建议,中,密钥类型硬编码RSA2048,internal/cert/store.go:337-339,现代实践倾向ECDSA P256，密钥更短握手更快，应做成可配置项,待确认,
```

各列说明：

| 列 | 说明 |
|---|------|
| 问题类别 | 资源泄漏/并发安全/错误处理/安全/配置与硬编码/数据一致性/死代码与可维护性/性能/运行时与运维/其他 |
| 严重程度 | 🔴 严重 / 🟡 需关注 / 🟢 建议 |
| 问题置信度 | 高（确定性缺陷）/ 中（大概率有问题）/ 低（疑似，需人工确认） |
| 问题 | 一句话概括问题 |
| 文件 | 文件路径和行号 |
| 问题阐述 | 问题的详细描述，包含为什么这是一个问题 |
| 处理进度 | 固定填写"待确认"。人工复核时改为"已修改"或"已忽略" |
| 处理结果 | 固定留空。人工复核时填写处理说明（如修改方式、忽略原因） |

注意：
- "处理进度"和"处理结果"两列由人工后续处理时填写，skill 生成时固定填"待确认"和空
- 每个问题独立一行，不要合并多个问题
- 问题阐述要具体到代码片段，不要泛泛而谈
- 行号必须来自实际源文件：CSV 中"文件"列的行号必须通过 grep 或读取实际源文件确认，不能使用 diff_report.md 的行号。diff_report.md 的行号是报告文件自身的行位置，不等于源文件的行号。

### 5. 汇总报告

审查完成后向用户报告：
- 审查文件总数
- 发现问题总数，按类别和严重程度统计
- CSV 文件路径
- 高置信度的严重问题简要列出

## 严重程度判定标准

- 🔴 **严重**：安全漏洞、数据丢失风险、生产环境可用性影响
- 🟡 **需关注**：潜在 bug、资源泄漏、并发隐患、错误处理不当
- 🟢 **建议**：代码风格、可维护性、性能优化、硬编码配置

checklist.md 中每个类别标注了"基准严重程度"，这是该类问题的默认判定。实际执行时可根据具体影响上下浮动：一个"配置与硬编码"问题如果直接影响生产安全，可以升为 🟡 甚至 🔴。

## 注意事项

- 不跳过任何变更文件，即使改动很小
- 对于生成的代码（如 protobuf、swagger 生成文件）、第三方依赖变更，可以简要说明后跳过详细审查
- CSV 使用 UTF-8 编码
